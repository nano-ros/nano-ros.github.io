## nano-ros layers

nano-ros on the RTOS is organized as five layers. Each layer has a defined boundary and can be tested independently.

### Application layer

Publishers, subscribers, timers, services, and control loops. This is where mission or robot logic lives. Application code is transport-agnostic — it never calls TAL functions directly.

### Interface layer (hardware_interface)

Connects hardware and device protocols to ROS 2 concepts. Every joint, sensor, and actuator is exposed as a typed `ros2_control hardware_interface`. The interface layer is generated by ros_HDL from the VHDL entity source. Application code interacts only with the abstract `nano_ros_hw_iface_t` interface — never with hardware registers directly.

### Runtime layer (rclc)

Keeps execution behavior deterministic. Static or bounded memory, absolute-timeline scheduling, single-threaded executor with a bounded handle count, zero heap in the hot path. `NANO_ROS_MAX_JOINTS` and all buffer sizes are compile-time constants.

### Transport Abstraction Layer (TAL)

Backend-agnostic publish/subscribe over a five-function-pointer interface. The TAL backend (SpaceWire/CCSDS, zenoh, 1553B, shared SRAM, or none) is selected at CMake configure time. Nothing above the TAL interface changes when the backend changes.

### FDIR layer

Fault Detection, Isolation, and Recovery. Compiled into every build that sets `NANO_ROS_FDIR_ENABLE`. Detects transport faults, stale commands, joint bounds violations, deadline misses, ECC errors, CRC mismatches, and URDF version mismatches. Emits PUS ST[5] events on APID 0x301. Transitions to per-joint safe positions on fault, not to zero.

## ros_HDL

ros_HDL is not a runtime component. It is a Python-based code generator that runs as a CMake pre-build step. It takes two inputs — a VHDL entity declaration and a URDF `<ros2_control>` block — and produces:

- `nanoros_<name>_hw.h` — register offsets and scaling constants
- `nanoros_<name>_hw.c` — `read()` and `write()` implementations with byte-swap and unit conversion
- `nanoros_<name>_sim.c` — software stub for host integration tests (no FPGA required)
- `nanoros_transport_apid.h` — CCSDS APID assignment derived from the URDF
- `nanoros_urdf_version.h` — SHA-256 hash of the URDF block (32-bit truncated) for version handshake
- `nanoros_yamcs_mdb.xml` — YAMCS Mission Database fragment for ground-system integration

The only thing that connects ros_HDL to the runtime is the `nano_ros_hw_iface_t` struct, which the generated code reads and writes. Everything above that struct is hardware-agnostic.

## MCU companion node

The MCU companion is not a compute node. It is a hardware safety net that runs independently of nano-ros software on a separate, simpler rad-hard processor. Its four responsibilities — FPGA configuration management, hard-RT FOC at 10 kHz, power health surveillance, and independent FDIR — are described in detail on the [MCU Companion](/architecture/mcu-companion/) page.

The key invariant: the MCU companion can reset or power-cycle the FPGA/SoC running nano-ros without any cooperation from nano-ros software. A nano-ros software freeze cannot prevent a hardware recovery.
